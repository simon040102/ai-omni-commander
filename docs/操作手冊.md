## 1. 系統需求與安裝

### 前置需求

| 項目 | 版本需求 | 說明 |
|------|---------|------|
| Node.js | >= 20.0.0 | 執行環境 |
| pnpm | 最新版 | 套件管理工具 |
| Claude Code CLI | 最新版 | AI Agent 核心，需已登入 |
| SVN CLI | >= 1.10 | 規格文件抓取（認證走 `--password-from-stdin`，需 1.10+；建議 SlikSVN） |
| Git | 最新版 | 版本控制 + 本地規格資料夾 pull |

### 安裝

```bash
git clone https://github.com/simon040102/ai-omni-commander.git
cd ai-omni-commander
git checkout OmniCommander_MCP

pnpm install
pnpm build
```

### SVN CLI 安裝

**Windows：**
- **推薦**：SlikSVN（[下載](https://sliksvn.com/download/)）— 純 CLI，自動加入 PATH
- **備選**：TortoiseSVN（需勾選 command line tools）

> 注意：TortoiseSVN 的 svn.exe 在 pipe 模式下會把中文字元變成 `?`。OmniCommander 已用 `--xml` 模式處理，但建議優先使用 PATH 上的 svn。

**macOS：**
```bash
brew install svn
```

### Claude Code CLI 安裝

```bash
npm install -g @anthropic-ai/claude-code
claude  # 首次執行會開瀏覽器 OAuth 登入
```

## 2. 啟動方式

### 方式 1：跨專案註冊（推薦）

**一次註冊，任何專案資料夾開 Claude Code 都能用。** 把路徑換成你的 clone 位置（**必須用絕對路徑**）：

```bash
claude mcp add --scope user omni-commander -- node "d:/暫存檔/claude code/ai-omni-commander-v5/server/dist/mcp-entry.js"
```

註冊後的行為：

- 在**任何資料夾**開 `claude`，OmniCommander MCP 自動 spawn，54 個工具直接可用
- `DB_PATH` 可省略 — MCP 自動解析到本 repo 的 `data/omni.db`，**與 cwd 無關**（MCP 啟動時會在 stderr 印出實際使用的 DB 路徑）
- 工具清單與 7 條使用規則由 MCP 協定連線時**自動注入**，不需要改任何 CLAUDE.md
- Web UI 即時更新需 Web Server (:3457) 在跑；**沒跑時工具照常可用**，只是 UI 不會即時反映

### 方式 2：在本 repo 目錄使用（.mcp.json）

在 ai-omni-commander 目錄開 Claude Code，讀 `.mcp.json` 後自動 spawn：
```bash
cd ai-omni-commander
claude
```

### 方式 3：MCP + Web UI 監控

```bash
# 終端 1：啟動 Web Server + Web UI（在本 repo 目錄）
pnpm dev
# Server: http://127.0.0.1:3457
# Web UI: http://localhost:5174

# 終端 2：開 Claude Code（任何資料夾）
claude
```

### 方式 4：VS Code 擴充

在 VS Code 裝 Claude Code 擴充；做過方式 1 的 user-scope 註冊後，任何開啟的資料夾都能用。

## 3. 首次設定

### 3.1 設定 Asana PAT / SVN 帳密

**推薦：直接在 Claude Code 裡用 `set_global_config` 工具**（不用手動改 DB）：

```
你：幫我設定 Asana PAT，token 是 1/xxxx...
→ set_global_config(key="asana.pat", value="...")

你：幫我設定 SVN 帳號 myuser 密碼 mypass
→ set_global_config(key="svn.username", ...) + set_global_config(key="svn.password", ...)
```

也可以用 Web UI 的 **Global Settings** 頁面設定。

### 3.2 建立專案

在 Claude Code 裡對話：
```
你：幫我建一個專案叫「我的專案」，前端在 D:\fork\my-ui，後端在 D:\fork\my-api
```

### 3.3 綁定 Asana 專案（可選）

```
你：列出 Asana 專案            → list_asana_projects 找 GID
你：幫我綁定 Asana，project GID 是 1234567890
```

### 3.4 設定 SVN 規格路徑（可選）

透過 Web UI 的 Project Settings，或請 AI 用 `update_project` 更新 `config_json`：
```json
{
  "svnConfig": {
    "frontendSpecPath": "https://svn.example.com/.../SA/",
    "backendSpecPath": "https://svn.example.com/.../SD/"
  }
}
```

### 3.5 設定本地規格資料夾（specFolders，可選）

規格若放在本地/網路磁碟或 git repo，可設定「規格資料夾」，抓規格時與 SVN 結果**合併**。透過 Web UI 的 Project Settings「規格資料夾」區塊，或 `update_project`：

```json
{
  "specFolders": [
    { "path": "D:\\specs\\tvedi-docs", "gitPull": true },
    { "path": "\\\\nas\\share\\規格", "gitPull": false }
  ]
}
```

安全規則（設定時自動驗證）：

- `path` **必須是絕對路徑**（MCP 可能從其他專案資料夾啟動，相對路徑一律拒絕）
- 與該專案的 frontendPath / backendPath **相同或互為父子一律拒絕**（防止誤 pull 程式碼 workspace）
- `gitPull: true` 時只做安全操作：working tree 乾淨才 `git pull --ff-only`；dirty → 跳過 pull 並警告；**絕不寫入、絕不 stash/reset**

### 3.6 確認安裝成功

```
你：有哪些專案
```
能列出專案就代表 MCP Server 正常。有異常（畫面沒更新、撈不到規格）先跑：
```
你：跑一下 health_check
→ 診斷 DB / Web Server / Asana PAT / SVN CLI 狀態
```

## 4. 現行工作流

```
列專案 → 同步 Asana → 選任務 → 自動判軌（bug 無規格→light / 規格驅動→full）
→ 抓規格（SVN + 本地規格資料夾雙來源）→ 抽規格檢查表（checklist）
→ [full 軌] Flow-Gated 開工閘（規格理解確認，原閘門 A）/ 完工閘（實作邏輯對齊，原閘門 B）→ 開發
→ 程式預檢（run_spec_compliance）→ AI 回對（獨立 agent 逐項驗證，missing=0）
→ 驗收（get_verification_plan + 證據上傳）→ completed（閘門放行）
```

- **自動判軌**：`get_execution_plan` 判斷 — taskType=bug 且無 SA/SD 規格 → **light 軌**（跳過流程圖閘門與 SA/SD 齊全檢查，檢查表改抽 BUG 原文）；否則 **full 軌**。輕的是工序不是標準：兩軌都要 AI 回對 missing=0 才能完成
- **接手舊任務**：任務已是 in_progress → 先 `resume_task(taskId)` 恢復脈絡
- **不知道做哪個**：`next_task(projectId)` 取得推薦

## 6. 完整操作流程

### Step 1：列出專案
```
你：「有哪些專案」
→ list_projects()
```

### Step 2：同步任務
```
選了專案後：
→ sync_asana_tasks(projectId)   // 5 分鐘內同步過會跳過；同步後自動偵測規格異動
→ list_pending_tasks(projectId)
→ 按功能代碼分組顯示（DF、WA、PM、SM...）
```

### Step 3：選任務
```
你：「WA04」
→ 問「要做前端、後端、還是都做？」
→ get_execution_plan(taskId) 自動判軌（full / light）
→ 已 in_progress 的舊任務 → 先 resume_task(taskId)
```

### Step 4：抓規格（full 軌）
```
→ fetch_svn_specs(projectId, taskId)     // SVN + 本地規格資料夾合併
→ find_axure_snapshot(projectId, code)   // Axure 原型
→ fetch_task_attachments(...)            // Asana 附件
→ 檢查規格齊全（前端需 SA+SD，後端需 SD）；缺 → 告知使用者，跳過須記 [SKIP]
→ （可選）check_spec_consistency(taskId) // SA/SD 矛盾比對 + 模糊點預檢；大規格才建議、使用者同意才跑
```

### Step 5：抽規格檢查表 + 流程圖閘門
```
→ 讀完規格後 save_spec_checklist(taskId, items)
→ [full 軌] save_task_flow(spec/plan) → report_flow_check（開工閘，gate="A"）通過才開發
```

### Step 6：確認後派 subagent
```
→ 列出找到的規格，問「有額外文件嗎？沒有說執行」
→ 使用者說「執行」→ Agent tool 派 subagent
   （前端 cwd=frontendPath / 後端 cwd=backendPath；prompt 用 get_execution_plan 的內容，
     只放規格路徑不放摘要；Extra Prompt 原封不動注入；派工前 save_task_dispatch 存快照）
→ 派工模型照政策帶：light 軌小 bug → sonnet；full 軌 implementer → opus（簡單規格可 sonnet）；
   AI 回對 reviewer / 基線修復 fixer → 永遠 opus；任務有 preferredModel 以它為準
   （get_execution_plan 回應會帶建議模型，照著帶即可）
→ 規格沒定義的 → subagent 用 report_spec_gap 記錄，不自行編造
→ 進度用 report_output / report_milestone 回報
```

### Step 7：回對 + 驗收 + 完成

見第 8 章。

## 7. 規格治理機制

| 機制 | 何時用 |
|------|--------|
| **規格缺口**（`report_spec_gap`） | 規格沒定義的欄位/API/邏輯——記錄後標 [NEEDS_CLARIFICATION] 繼續其他部分，寧可不做也不要做錯。Web UI Dashboard 的「待補規格」面板可追蹤 |
| **規格裁決落地**（`resolve_spec_gap`） | 使用者對缺口拍板後**立刻**呼叫，resolutionNote 必填具體裁決（≥5 字，「可以/好/照舊」等空泛詞拒絕）。裁決效力等同規格：自動注入後續派工 prompt、resume_task、AI 回對計畫。**嚴禁只把答案手寫進 prompt 或對話帶過**——不落地下游看不到。任務結案時仍有未裁決缺口會附提醒（不擋門） |
| **專案經驗筆記**（`save_project_note`） | 發現專案特有的坑/慣例（規格沒寫但必須遵守）就記，之後每個 execution plan 自動注入 |
| **規格異動偵測**（`check_spec_changes`） | Asana 同步後自動跑；也可手動跑。規格在開工後被改 → 自動開 `spec_changed` 缺口，提示重新 fetch_svn_specs |
| **SA/SD 一致性 + 模糊點預檢**（`check_spec_consistency`） | 兩維度：SA↔SD 矛盾比對（規格自相矛盾時實作永遠無法 100% 回對）＋規格模糊點預檢（決策點開 `ambiguous_spec` 缺口給使用者拍板；advisory 不擋工）。不是每次都跑——full 軌大規格由 orchestrator 建議、使用者同意才跑，絕不自動觸發 |

## 8. 驗證與完成閘門

### 8.1 規格回對（兩步，通用）

1. **程式預檢**：`run_spec_compliance(taskId)` 用程式比對 checklist 與程式碼，抓文字/路徑錯字並修掉。**advisory 性質，不解鎖完成閘門**；有正當理由的項目用 `waive_checklist_item` 豁免並附理由
2. **AI 回對（完成閘門依據）**：`get_compliance_review_plan(taskId)` 取派工計畫 → 派**獨立的 AI 審查 subagent**（絕不可由寫 code 的 implementer 自評；**模型永遠帶 opus**）讀規格原文 + checklist + 程式碼逐項判定 → `save_compliance_review` 寫回。**最新 AI 回對 missing=0 才可標 completed**；missing>0 → 交回 implementer 修正後重新回對。**修正後的重審自動走增量模式**：reviewer 只重判上輪 missing / 新增 / 有疑慮項，上輪 matched 的字面項由 `save_compliance_review(carryForward=true)` 程式重驗證據自動沿用（logic 項每輪必重判），閘門標準不變

### 8.2 orchestrator 自行驗證

#### 後端任務
1. **靜態檢查**：grep ServiceImpl 有沒有 `findAll()`
2. **DDL 比對**：CREATE TABLE 欄位名 vs Entity @Column name
3. **API 煙霧測試**：curl 每個新 API，確認回 200 不是 500
4. **seed SQL 檢查**：INSERT 欄位數 = VALUES 參數數

#### 前端任務
1. **tsc --noEmit**：TypeScript 零錯誤
2. **瀏覽器測試**：Playwright 開頁面操作（服務有跑的話）

**單元測試只驗邏輯，不驗 SQL 和欄位名。API 煙霧測試才是真正的驗收。**

### 8.3 驗收清單與完成

```
→ get_verification_plan(taskId)           // 依 label 取驗收清單
→ 逐項執行 → report_verification_result(taskId, results)
→ 有截圖/報告 → report_verification_evidence(taskId, filePath)
→ update_task_status(taskId, "completed", summary)
   // 受六道完成閘門管制：完工閘（實作邏輯對齊）/ 檢查表存在 / AI 回對 missing=0 /
   // 單元測試 / 執行計畫或派工記錄（track、[TRACK]、[DISPATCH] 其一）/ 驗收 FAIL 擋結案；
   // skipFlowGate 限使用者明確同意，會記 [SKIP]
→ 失敗必標 update_task_status(taskId, "failed", "原因")，否則永遠卡在 in_progress
```

## 9. Web UI 監控（可選）

啟動 Web Server 後開 `http://localhost:5174`。

### 功能
- **Dashboard**：專案概況、任務狀態、agent 輸出、里程碑
- **規格治理收合區**（Dashboard 內三面板）：
  - **待補規格** — report_spec_gap 的缺口清單；點「解決」需填**具體裁決內容**（必填，空泛詞擋下），已裁決的以「裁決紀錄」呈現（不劃掉、裁決文字醒目——等同專案補充規格清單）
  - **規格回對** — checklist 項目 + 比對結果（matched / missing / waived）
  - **專案筆記** — save_project_note 累積的經驗
- **Tasks**：任務清單、狀態追蹤（可切換依截止日排序，逾期紅字）
- **Settings**：Global Settings（SVN 帳密、Asana PAT、桌面通知開關）、Project Settings（SVN 規格路徑、**規格資料夾**、Extra Prompt、Asana 綁定、外部 DB）
- **Gen Skills**：觸發產生 workspace 的 CLAUDE.md + skills

### 通知

## 10. 規格文件來源（SVN + 本地資料夾）

`fetch_svn_specs(projectId, taskId)` 從**兩個來源合併**抓取：

### 來源 1：SVN

1. 從任務 `parent_name` 提取功能代碼（`WA04_已轉派工作清單` → `WA04` → root code `WA`）
2. `svn list --xml` 搜尋匹配資料夾（如 `WA流程作業區/`）
3. 遞迴搜尋 `.docx` / `.pdf`，下載到 `data/uploads/{projectId}/`
4. `.docx` 自動轉 `.md`（mammoth + turndown）
5. 三層快取：SVN last-modified → SHA-256 hash → DB 記錄

### 來源 2：本地規格資料夾（specFolders）

- 功能代碼比對邏輯與 SVN 相同（root code + 檔名/路徑段命中 + 中文名 fallback + `0_共用` fallback）
- docType 由檔名慣例推斷（SA/SD token 或「需求規格/系統分析/系統設計」，預設 SD）；**.html/.htm 也收**（視為 Axure 原型，標 [HTML] 綁任務給前端 agent）
- git 資料夾先安全 pull（dirty → 跳過 + 警告；子資料夾也能偵測 git repo——往上找 .git）；版本記錄用 git 檔案 commit 日期或 mtime
- 部分來源失敗 → 文件區塊列警告；全失敗 → `[SPEC_FETCH_ERROR]`

### 注意事項

- Windows 上 TortoiseSVN 的 `svn list` 純文字輸出會把中文變 `?`，已改用 `--xml` 模式
- SVN URL 中的中文自動 percent-encode
- SVN 認證走 `--password-from-stdin`（需 svn >= 1.10）

## 11. Asana 任務整合

### 架構

`sync_asana_tasks` 直接用 PAT token 打 Asana REST API，不依賴 Web Server。

### 同步邏輯

1. 從 `global_config` 取 `asana.pat`
2. 從專案 `asana_project_gid` 取 Asana 專案 ID
3. 打 Asana API 取任務（含分頁），upsert 到本地 tasks 表
4. **subtask 遞迴抓取**：專案清單抓不到未掛進專案的 subtask（工作項目常在第二、三層），自動對未完成任務遞迴抓 subtask（深度上限 3、只抓未完成、gid 去重、每次上限 300 支 API 超過截斷+警告；`includeSubtasks=false` 退回舊行為）
5. **截止日與欄位繼承**：due_on 落地到 `tasks.due_date`；subtask 沒填截止日 → 繼承最近有日期的祖先任務；「功能代碼」custom field 同樣往下繼承；section 繼承根任務
6. 5 分鐘內同步過自動跳過（`force=true` 覆蓋）
7. **同步後自動跑規格異動檢查**（有變更 → 自動開 spec_changed 缺口並警告）

`next_task` 推薦時，同優先級內逾期/近到期優先（無截止日排最後），推薦理由帶到期資訊（如「已逾期 2 天」）。

### 任務分類（regex）

| 標題關鍵字 | 分類 |
|-----------|------|
| 前端、串接 | label: frontend |
| 後端 | label: backend |
| bug、fix、錯誤、失效 | taskType: bug |
| 新增、開發 | taskType: feature |

### 其他

- `get_asana_task_comments` 支援 omni UUID 或 Asana GID
- `fetch_task_attachments` 下載附件（BUG 截圖等）
- Asana 保持唯讀，不做回寫

## 13. 疑難排解與注意事項

### 先跑 health_check

畫面沒更新、撈不到規格、Asana 同步失敗 → 先跑 `health_check`，會逐項診斷 DB / Web Server / Asana PAT / SVN CLI。

### 重要原則

1. **Orchestrator 不直接改專案程式碼** — 全部派 subagent
2. **不在 prompt 中摘要規格** — 只放檔案路徑，subagent 自己 Read
3. **規格沒定義不可編造** — report_spec_gap 記錄，寧可不做也不要做錯
4. **裁決回答當下就落地** — 使用者對缺口拍板後立刻 resolve_spec_gap 寫 DB，嚴禁只手寫進 prompt（下游全部從 DB 自動注入）
5. **completed 有六道閘門** — 完工閘（實作邏輯對齊）/ 檢查表 / AI 回對 missing=0 / 單元測試 / 執行計畫或派工記錄 / 驗收 FAIL 擋結案，全過才放行
6. **簡單功能合併 agent** — 前端+串接同 workspace，避免衝突
7. **接手舊任務先 resume_task** — 恢復完整脈絡再動工

### Windows 特別注意

- `tsx watch` 在 Windows 上不穩定，改 `.ts` 後**手動重啟 server**
- SVN 輸出用 `--xml` 確保 UTF-8（避免 CP950 亂碼）
- Server 預設綁 `127.0.0.1`（`HOST` env 可改 `0.0.0.0` 供區網存取）

### Agent 並行建議

同時執行的 subagent 不超過 5 個，避免系統資源不足。
