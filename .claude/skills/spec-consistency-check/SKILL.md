# 規格一致性檢查（規格 ↔ 規格）

**規格自己站不站得住。** 規格自相矛盾時，寫出來的程式永遠無法 100% 對得上——因為根本沒有一個「對」可以對。

這件事只需要規格文件。不用程式碼、不用起服務、不用資料庫。**成本最低，卻最常被跳過。**

## 什麼時候做

**開工前。** 這是它唯一划算的時機。

實測依據：某支功能（PP001，SA 362 行 + SD 979 行）事後找出 42 條規格問題，其中 **17 條純讀規格就抓得到**，卻一路拖到抽檢查表和逐條驗證程式碼時才浮現——那是最貴的階段。

已經開工了也值得補做，至少讓後面的「規格沒寫怎麼辦」有個清單可以一次拍板，而不是每撞到一次問一次。

## 開始前要有

| 要什麼 | 說明 |
|---|---|
| SA（系統分析）規格 | 前端／畫面行為的來源。只有 SD 也能做，但維度一會少一半 |
| SD（系統設計）規格 | 後端／API 的來源 |
| **共用規格文件** | 規格寫「參見 `Common.md`」時**必須一併取得**。少了它，凡是牽涉共用功能的模糊點全部只能標「未查證」——那正是本份警告會變成噪音的產出 |
| 畫面稿 | **含 SA 內嵌的圖片**（`![](../../Images/xxx.png)` 那些），不是只有外部 Axure。**這些圖要逐張打開看**——分頁怎麼呈現、某欄位到底在不在畫面上，答案常常只在圖裡 |
| 專案慣例（選配） | 共用元件的既定行為、團隊約定。規格沒寫但團隊都知道的，不算模糊 |
| 舊程式（選配） | 重構型 SD 常以舊程式為權威（「忠實還原 `XxxAction.java:323-362`」）。沒有它的話，這類條目標「**需對照舊程式才能裁決**」，不要當成純讀規格就能定案 |

**只讀不改。** 這份工作不寫程式、不改規格檔，只產出清單交人裁決。

---

## 三個維度，都要做完

```
維度一  SA ↔ SD          跨文件矛盾
維度二  同一份文件內部     自己前後打架     ← 最容易漏，也最容易抓
維度三  模糊點預檢         實作時會被迫用猜的決策點
```

---

## 維度一：SA ↔ SD 矛盾比對（四個面向都要做完）

| 面向 | 比什麼 |
|---|---|
| **欄位對齊** | SA 畫面上每個欄位（名稱／型別／必填／預設值）↔ SD 的 request／response 欄位。名稱不一致、SA 有 SD 沒有、型別矛盾都列出 |
| **功能覆蓋** | SA 描述的每個操作（查詢／新增／儲存／刪除／匯出…）↔ SD 有沒有對應 API |
| **反向檢查** | SD 定義了、但 SA 完全沒有對應畫面或操作的 API（規格可能漏更新） |
| **訊息與驗證規則** | SA 的錯誤訊息／驗證規則 ↔ SD 的邏輯規則。如 SA 說必填、SD 參數 optional |

實例：

> SA 標「付款日期（起）」為必填且有不可空值檢核；SD 的 `payDateS` 必輸欄留空（選填），SQL 還以「空值不過濾」守衛。
> 結果：前端加了必填、後端沒加。同一個矛盾，前後端各自解讀。

## 維度二：同一份文件內部矛盾（最容易漏的一塊）

**SA↔SD 比對抓不到「SD 自己跟自己打架」。** 前者是跨文件比對，結構上就不會去看同一份文件的前後段。

實測依據：PP001 那 42 條裡，**驗證階段才浮現的 20 條有 10 條是 SD 內部矛盾**——純讀一份 SD 就抓得到，卻等到最貴的階段才撞出來。

### SD 內部要對五組

| 比什麼 | 為什麼會打架 |
|---|---|
| **欄位定義表 ↔ SQL 參考** | SQL 查了表，欄位表沒列；或欄位表有，SQL 沒用到 |
| **SQL 本體 ↔ 實作備忘** | **兩者版本可能不同步，哪邊新要看版本管控歷程**。不要預設哪邊是基準——實務上兩種都遇得到：備忘是後來依實測回填的最新資訊，或 SQL 改了備忘沒跟上 |
| **INPUT／OUTPUT 表 ↔ 格式範例** | 範例是複製來的，欄位表是重寫的 |
| **章節 ↔ 章節** | 同一個欄位在 §1 和 §5 講的不一樣 |
| **規範敘述 ↔ 同節 SQL** | 文字說可以，SQL 寫死做不到 |

### SA 內部要對四組

前面那五組是 SD 的文件結構（SQL、實作備忘、INPUT/OUTPUT 表），套不到 SA。SA 有自己的四組：

| 比什麼 | 為什麼會打架 |
|---|---|
| **欄位說明表 ↔ 畫面稿圖片** | 表裡列了欄位，圖上找不到；或圖上有，表裡沒說明 |
| **欄位說明表 ↔ 按鈕說明表** | 按鈕說「儲存後回列表」，欄位表沒有對應的必填定義 |
| **畫面章節 ↔ 輸出報表章節** | 列表少一欄，報表卻有（或反過來） |
| **檢核規則 ↔ 訊息文字** | 說了要檢核，沒給訊息文字；或給了訊息，沒說什麼情況觸發 |

**只做 SD 不做 SA，維度二等於只做一半。** 兩邊都要走。

### 六個真實案例（全部出自同一份 SD）

| 矛盾 | 位置 |
|---|---|
| `userAccount` 標必輸且註明由 header 取得，同一節的格式範例卻是純 GET path，連 header 都沒提 | §3 / §4 |
| 同一個 `userAccount` 在 §5 標 header，同節範例放在 JSON body | §5 |
| INPUT 說可依 `sortField` 排序，同一節的 SQL 參考寫死 `ORDER BY A.payDate DESC` | §1 |
| 實作備忘說「段 4~7 的 `security1` 是空字串字面值」，同節 SQL 本體段 4/5 取的是 `ISNULL(B.SECURITY1,'')` 欄位 | §1 |
| TABLE 清單沒列 `CODE_LIST`，同節說明第 5 點明訂代碼來源就是 `CODE_LIST` | §1 |
| §1 OUTPUT 列了 `beneficiaryBankId`，§5 說明 2 卻標「畫面列表無」 | §1 / §5 |

### 一條判準

**同一份文件裡，同一件事被寫了兩次以上，就要對一次。** 規格越長越容易出現——寫的人自己也記不住前面怎麼寫的。

### 只檢某一節時，「章節 ↔ 章節」必須降級

這一組本質上要跨節才做得到（`setCodeName` 只在 §5 說「僅下載用」、`kindNo` 的下拉來源在 §6）。範圍被限定成單一節時：

**把它降級為「待跨節確認清單」並在報告明白標出**。不標的話，被限定範圍的人會靜默漏掉這一組，**而且報告看起來跟做過一樣**。

### 長規格先折疊再建索引

長規格（500 行以上）要先建一張「同一個欄位／參數在哪幾處被提到」的索引，但**直接 grep 會被複製結構打敗**：`payDateS` 在某份 SD 出現 20 次以上，其中 14 次是 7 段 UNION 裡逐段複製的同一句守衛，真正的「被提了兩次以上」反而淹掉。

可行的順序：

1. **先折疊重複結構** —— 多段 UNION／多個相似 API 收成「一段完整 + 段間差異表」
2. 再對折疊後的內容建索引
3. 逐個比對

## 維度三：模糊點預檢（以實作者視角走決策樹）

把自己當成即將實作這個任務的工程師，逐一走過規格描述的**每個畫面／欄位／按鈕／流程**，在每個決策點問：

> 「做到這裡，這個決定能從規格找到唯一答案嗎？」

找不到答案、或存在兩種以上合理讀法 → 模糊點候選。

### 先查再報（防噪音的成敗關鍵）

宣告任何模糊點之前，**必須先自查四處**：

1. **規格全文其他章節** —— 答案常寫在別的段落
2. **原型** —— 有畫面稿就對照。**原型畫出來的行為就是答案**
3. **專案慣例** —— 共用元件的既定行為、團隊約定，已涵蓋的不算模糊
4. **已經開過的問題清單** —— 專案有在追蹤規格問題的話（issue、待補規格清單、上次的檢查報告）就先查，別重複開同一條。**沒有這種清單就跳過這項並在報告註明**

查得到答案的**不是**模糊點。這一步不做，產出會是一大堆噪音，然後整份清單被丟掉。

**四處自查有做不到的，要能誠實記錄。** 拿不到共用規格、沒有畫面稿、專案慣例問不到人——這些都會發生。報告的每一條模糊點加一欄「自查完成度」，寫「四處皆查」或「未查證：缺共用規格文件」。**沒有這一欄，做不到的自查只能被動吞掉，那比缺前置更糟**——讀的人會以為每條都查過四處了。

### 明文排除（不算模糊點，禁止吹毛求疵）

- 用詞風格、排版偏好
- 實作自由度內的選擇（變數命名、內部結構、程式怎麼組織）

### 每條要寫三件事，缺一不可

| 要素 | 例子 |
|---|---|
| **規格出處** | `SA WA05.md §3.2` |
| **具體哪個決定沒答案** | 「刪除要不要二次確認——§3.2 只寫『可刪除』，沒寫確認流程」 |
| **可能的選項** | 「A：直接刪除 / B：confirm 彈窗後刪除」 |

**選項想不出來就寫「選項未知：需 SA 提供」，不要編。** 有些決定本來就沒有可枚舉的選項（某欄位的序列化格式、某代碼的對應表），硬湊出「A：JSON / B：key=value / C：其他」是**假選項**，跟「不可自己替規格挑一邊」的精神直接相衝。寫「選項未知」不算違反三要素。

**禁止「規格不清楚」「XX 沒寫清楚」這種沒有出處的空泛描述。** 那種寫法讓人無法拍板，等於沒寫——「沒有選項」和「沒有出處」是兩件事，前者可以接受，後者不行。

## 判定紀律

- **每條矛盾必附兩邊出處**：**檔名 + 章節路徑 + 引一句原文片段**（行號選配）。同一份 SD 裡常有 6 個 `#### INPUT`、6 個 `#### 說明`，光寫「§1 說明」定位不到；而行號只有讀 .md 原始檔的人對得上，PM／SA 用預覽看根本找不到——所以**引原文片段才是可靠的定位方式**。維度二要附同一份文件的兩個位置
- **不確定是不是矛盾 → 列為疑問，不要斷定**。疑問單獨一區，請人判斷
- **前提下永不成立／自我抵銷的敘述算矛盾，不算疑問。** 例：取段表某一列的前提是「A 為空且 B 為空」，同一列的額外條件欄卻寫「加上 `B LIKE '%'+:B+'%'`（B 為空時不加）」——在該列前提下這欄永遠不成立。這是寫的人複製貼上沒清乾淨，歸維度二
- **SD 越界寫實作細節**（「建議用 `BigDecimal.longValueExact()`」、「`@Column` 應宣告 `precision=18`」）**內部一致就不列**。那是規格越界，不是規格矛盾；要列的話單獨一區標「規格越界寫實作」，不要混進矛盾清單
- **不可自己挑一邊**。看起來哪邊比較合理都不算——挑了就等於你替使用者做了決定，而且沒人知道你挑過
- **沒有發現也要講清楚，而且分開計。** 「N 個欄位」有三種算法（SA 畫面欄位／SD INPUT+OUTPUT／SQL 投影欄位 × 段數）差一個數量級，混在一起統計就失去意義。照這個格式報：

  ```
  SA 畫面欄位 28 個、SD INPUT 21 個、SD OUTPUT 25 個、SQL 投影 38 欄（7 段）
  API 6 支
  同一件事被寫兩次以上的 12 處
  ```

  不可含糊帶過或省略統計。**「沒問題」和「沒檢查」看起來一樣，數字是唯一能分辨的東西。**

## 報告格式

```markdown
# {功能代碼} 規格一致性檢查

| 項目 | 內容 |
|---|---|
| 規格 | SA `路徑`（N 行）<br>SD `路徑`（M 行） |
| 檢查日期 | |
| 涵蓋範圍 | 見第一節（分開計） |

## 一、結果總表

| 維度 | 條數 |
|---|---:|
| SA ↔ SD 矛盾 | |
| 同一份文件內部矛盾 | |
| 模糊點（待拍板） | |
| 疑問（不確定是否矛盾） | |
| 待跨節確認（只檢部分章節時） | |

**涵蓋範圍**（分開計，不要合成一個數字）：
SA 畫面欄位 N 個、SD INPUT N 個、SD OUTPUT N 個、SQL 投影 N 欄（N 段）／API N 支／同一件事被寫兩次以上的 N 處

**建議先拍板的順序**：（會直接影響實作對錯的排前面）
※ **排序可以挑，內容不可以刪。** 下面每一節都全列。

## 二、SA ↔ SD 矛盾（N 條）

| # | 面向 | SA 說 | SD 說 | 兩邊出處 |
|---:|---|---|---|---|

## 三、同一份文件內部矛盾（N 條）

| # | 哪份文件 | 位置 A 說 | 位置 B 說 | 兩處出處 |
|---:|---|---|---|---|

## 四、模糊點（N 條，待拍板）

| # | 出處 | 哪個決定沒答案 | 可能的選項 | 自查完成度 |
|---:|---|---|---|---|

## 五、疑問（N 條，不確定是否矛盾／不確定該歸哪一類）

寫清楚為什麼不確定，請人判斷。模糊點與矛盾之間拿不定的也放這裡。

## 六、規格越界寫實作（N 條，僅供參考）

內部一致但屬於 SD 寫進實作細節的，列在這裡，不混進矛盾清單。
```

**全列，不挑重點。** 挑掉的那條往往就是下一個人踩到的。

**但同一個根因可以併成一條** —— 例如「OUTPUT 表少了 16 個 SQL 投影欄位」寫一條、把 16 個欄位名列齊，不要拆成 16 條。那 16 條是同一次裁決，拆開會把其他真正獨立的問題灌到看不見。

量大就按維度分組，但不可只留摘要。某支功能那次 42 條全列，讀的人才知道規格的真實狀態。

## 白話鐵律

報告是給**人**看的（PM、SA、客戶），不是給工具看的。

- 不要用內部術語（`sa_sd_mismatch`、`ambiguous_spec` 這類分類代號）
- **分類標籤不能取代原因**。不要寫「這條屬於欄位對齊問題」，直接寫「SA 標必填、SD 標選填，前後端會各做一套」
- 交叉引用要叫出名字，不要寫「見第 5 條」——讀者得回頭數

## 跟另兩份的分工

| 這份不管，交給誰 |
|---|
| 程式有沒有照規格做 → `spec-compliance-review`（讀規格 + 讀程式碼逐條核對） |
| 跑起來會不會壞 → `verifying-end-to-end`（真服務、真 DB、真瀏覽器） |

**這份是三份裡最先做的**，而且做完能讓後面兩份省事：規格矛盾先解決，程式回對才有一個明確的「對」可以對。

## 絕對禁止

- 自己替規格挑一邊（挑了就是你在定規格，而且沒留痕跡）
- 沒查過其他章節／原型／專案慣例就宣告模糊點（那是噪音，會讓整份清單被丟掉）
- 模糊點只寫「規格不清楚」而沒有出處（沒有選項可以接受，寫「選項未知：需 SA 提供」；沒有出處不行）
- 為了湊滿三要素而編出假選項
- 只做 SA↔SD 就收工（同一份文件內部矛盾是另一半，而且往往更多）
- 只檢 SD 內部、不檢 SA 內部
- 沒打開 SA 內嵌的畫面稿圖片就宣告模糊點
- 拿不到共用規格文件卻不在報告註明，讓「未查證」看起來像「查過沒問題」
- 只檢某一節時，把「章節↔章節」靜默跳過
- 矛盾只挑重點列
- 修改規格檔或程式碼（只讀，產出是清單）
- 沒發現矛盾就不寫統計（「沒問題」和「沒檢查」看起來一樣，要能分辨）
