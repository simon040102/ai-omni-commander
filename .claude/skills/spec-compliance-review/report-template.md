# 報告骨架

照這個順序寫。所有用字先過一遍 SKILL.md 的「報告白話鐵律」。

---

```markdown
# {功能代碼} {功能名稱} — 程式 ↔ SA/SD 規格回對

| 項目 | 內容 |
|---|---|
| 功能 | |
| 回對日期 | |
| 規格怎麼寫 | SA `路徑`<br>SD `路徑`（N 行） |
| 程式 | 前端 `路徑`　後端 `路徑` |
| 怎麼做的 | 把規格拆成逐條檢查項 → 程式自動比對一遍 → 換一個**沒參與過實作的 AI** 逐條開檔驗證 → 資料表欄位另外拿去問實體資料庫 → 它給的每個程式碼位置再由程式重新核對一次 |

---

## 一、結果總表

先把規格拆成 N 條可逐一檢查的項目，再用兩種方式各驗一遍：

| 驗法 | 總項數 | 符合 | 不符 | 需人工判斷 | 這個結果算不算數 |
|---|---:|---:|---:|---|---|
| 程式自動比對 | | | | | **不算** —— 只能比對文字，看不懂行為 |
| **AI 逐項開檔驗證** | | | | — | **算** —— 每筆都要指出程式碼在第幾行 |

**反向掃描**：重讀規格後補抽了 N 項（沒補到就寫「反向掃描無遺漏」）。
※ 這一行不可省略——不然讀者無從判斷上表的項數是不是就是全部。

**N 項不符要分成兩類看，處理方式完全不同：**

| 分類 | 數量 | 要做什麼 |
|---|---:|---|
| **A. 程式真的做錯或沒做** | | 要修（見第二節） |
| B. 程式是對的，是驗證方式抓不到 | | 不用修（見第三節） |

**不符集中在哪：**（依檢查類型列出符合/不符）

## 二、程式真的做錯或沒做（N 項，要修）

### 1. {一句話講清楚哪裡壞了}

| | |
|---|---|
| 這是什麼 | 行為規則 / 畫面上的文字 / API 路徑… |
| 規格怎麼寫 | 原文 + 章節 |
| 程式實際狀況 | `檔案:行號` 實際怎麼寫 |

（補充說明）

**使用者會遇到什麼**：具體症狀，不要寫「不符合規格」。

**怎麼修**：改哪個檔案、改成什麼。

## 三、程式沒問題，是驗證方式抓不到（N 項）

**直接寫發生什麼事，不要只給分類標籤。** 例如：
> 前端是用 `` `${API_RELATED_LIST}/${type}/...` `` 組出路徑的，路徑常數與 method 不在同一行，逐行比對抓不到。程式本身沒問題。

**每一節結尾回頭檢討檢查表。** 抓不到常常不是驗證方式的錯，是檢查項當初抽錯粒度：
> 把 `TRDETAILKIND` 這種常數值直接寫進路徑、或把帶 `{}` 參數的完整路徑當一整串文字來驗，注定驗不過。下次應該拆成兩項——路徑骨幹一項、路徑參數另一項。

## 四、程式檢查與 AI 判斷結論相反的（建議人工複核）

兩邊為什麼會相反，各自的理由是什麼。

## 五、規格矛盾／未定義（交使用者裁決）

**全列，不挑重點。** 不可自行取捨——挑掉的那條往往就是下一個人踩到的。每項寫：規格哪裡矛盾、目前程式怎麼做、出處在哪。

量大就分兩組（性質不同，處理的人也不同）：
- **讀規格階段就發現的** —— 規格自己矛盾，不看程式也成立
- **對照程式碼才浮現的** —— 規格看似完整，實作時才發現無法唯一決定

## 五之二、反向對齊：程式有、規格沒定義的欄位

沒有也要寫「無多餘欄位」。有的話每項寫：哪支 API、哪個欄位、是過度實作還是規格待補（不要自己決定，交裁決）。

## 五之三、資料表欄位

**兩段分開寫，因為前一段不需要資料庫連線、後一段需要。**

### DDL 檔 ↔ Entity（不需連線，一定有做）

| 落差 | 欄位 | 解讀 |
|---|---|---|
| DDL 有、Entity 沒有 | | 程式沒用到（可能漏做） |
| Entity 有、DDL 沒有 | | DDL 檔沒更新，或 Entity 對錯表 |

沒有落差就寫「逐欄一致，含系統共用欄位」。

### 對實體資料庫（需要連線）

幾個確實有、幾個沒有、幾個無從判定。無從判定要列出是哪些表、為什麼撈不到。
**沒做實體核對就寫「本次未做」**，並說清楚現有證據強度到哪（有 Entity 佐證 vs 只有原生 SQL 字串佐證，可信度差很多）。

## 六、建議優先處理

**先寫出排序準則**（例：依「上線後被發現的機率 × 後果」排序，最終優先權由使用者判斷），再列清單。沒寫準則的排序，讀者不知道憑什麼這樣排，也就無法反對。

缺陷若在共用元件／共用 hook／共用 API，這裡要標明**還有哪些功能會中招**。

## 七、檢查表範圍外的發現

跨切面的錯誤處理、整支模組沒有單元測試、共用元件的坑——這些不會是任何一條檢查項，但常常比表內的更嚴重。沒有也要寫「無」。

## 八、逐條結果明細

AI 逐項驗證執行於 {日期}，共 N 項。
**「程式碼位置」那一欄不是 AI 說了算** —— 每一筆都被程式重新打開檔案核對過：檔案在不在、行號有沒有效、是不是編譯產物目錄、那一行前後 10 行內是不是真的有規格寫的那串文字。有任何一筆對不上，整批退回重驗。

狀態：✅ 符合（附程式碼位置）　❌ 不符（需處理）　➖ 已豁免

> 每類之中 **不符的排在最前面**。不符的完整原因見第二、三節。

### API 路徑與 HTTP 方法　（N 項：✅ x　❌ y）

| # | 狀態 | 檢查項 | 程式碼位置 | 規格出處 |
|---:|:--:|---|---|---|

（其餘分類同上：行為規則（畫面怎麼動、後端怎麼算）／畫面上的文字／送給後端的參數／後端回傳的欄位／資料表欄位）
```

---

## 表格的實務注意

- **最多五欄。** 多一欄，證據那欄就會被擠成一個字一行，整張表報廢
- 表格內的 `|` 要跳脫成 `\|`，換行要換成空白，否則會拆欄／斷列
- 長路徑省略共同前綴，開頭註明省了什麼（例：`MainService/…/` = `MainService/src/main/java/com/uec/main/`）
- 規格出處欄每列的檔名都一樣，只留章節
