# 規格回對（程式 ↔ SA/SD 一致性）

逐項驗證「實作出來的程式」與「SA/SD 規格文件」是否一致。

核心設計：**AI 負責判斷，程式負責讓 AI 不能唬爛。**
檢查表定義要驗什麼、程式預檢抓字面錯、獨立 AI 判語意邏輯、證據驗證器逼 AI 指出原始碼位置。

拿掉任何一層都會退化：只有 AI → 它會用「應該有實作」矇混；只有程式 → 行為規則完全驗不到。

## 輸入

| 要什麼 | 說明 |
|---|---|
| 規格文件 | SA（前端）／SD（後端）原始檔路徑。**必須讀原文**，不可用任何人的轉述或摘要 |
| 共用規格文件 | 規格寫「參見 `Common.md`」時**必須一併取得**。少了它，凡是用到共用功能的項目全部只能標「未查證」 |
| 程式碼 workspace | 前端／後端專案根目錄（可各一個） |
| 檢查表 | 沒有就在第一步現抽 |
| Node 18+ | 跑 `scripts/spec-check.mjs`（零外部套件，不用 npm install） |
| DB 連線（選配） | 第四步用，唯讀就夠。沒有就跳過那步並在報告寫明 |
| 實測產出（選配） | 功能測試留下的 DOM 文字／API 實際回應／DB 查詢結果，第三步可當證據 |

## 流程

```
1 抽檢查表 → 2 程式預檢(advisory) → 3 獨立 AI 逐項驗證 → 4 實體 DB 核對 → 5 證據程式重驗 → 6 寫報告
```

**寫 code 的人不可以驗自己的 code。** 看過自己怎麼寫的，就會用「應該有實作」矇混過去。

抽檢查表的人**可以**兼任驗證（小規格建議這樣，剛讀完規格的人知道哪裡有陷阱，交接會把這些丟掉）。但大規格分開比較好：**抽表時的取捨會變成驗證時的盲點**——當初判斷「這條不用抽」的人，驗證時也不會發現它漏了。這時反向掃描那一步就形同虛設，因為是同一個人的同一個盲點。

## 第一步：抽檢查表

讀規格原文，拆成結構化檢查項，存成 JSON（見 `checklist.schema.md`）。

| itemType | 內容 | 例子 |
|---|---|---|
| `ui_text` | 畫面上的字面文字 | 按鈕「查詢」、訊息「請選擇 退件原因」 |
| `api` | API 路徑 + method | `POST /fedi/cm004/search` |
| `param` / `response_field` | 送出的參數 / 回傳的欄位 | `pagination.pageSize` |
| `db_field` | 資料表欄位 | `ADM_CUST_LOG.OID` |
| `logic` | 行為規則 | 「退件時 backreasonId 才有值」 |

抽取紀律：
- 行為敘述句（「點擊 X 後…」）存 `logic`，不存 `ui_text`
- `ui_text` 只放程式中應該存在的字面文字
- 每項必附 `sourceRef`（規格章節），之後報告要引用
- 標 `side`（frontend / backend），決定去哪個 workspace 掃

抽的時候順手記下**規格自相矛盾或沒定義**的地方，別自己替它決定 —— 那些進報告的「規格矛盾／未定義」一節，交使用者裁決。

### 規格寫「參見共用功能」時，要跟過去讀

一定要跟過去。同一節不跟過去讀只有 4 項，跟過去讀有 18 項——**差一個數量級**。

母規格通常只寫「呼叫共用『取得系統代碼下拉選單』，詳細欄位／SQL 參見 `../COMMON/Common.md`」，真正能抽出檢查項的 INPUT／OUTPUT／SQL 全在共用規格裡。

**共用 API 的呼叫端與實作端各算一項。** 同一個 content 出現兩次是正解，不是味道不對：

| id | itemType | side | content | 驗什麼 |
|---|---|---|---|---|
| 1 | api | backend | `GET /system/codeType/getOneWithCode/{code}` | handler 真的存在 |
| 2 | api | frontend | 同上 | 前端真的呼叫 |

### API 路徑要拆成兩項：骨幹 + 參數

規格常把具體值寫進路徑（`/getOneWithCode/TRDETAILKIND`），共用規格寫的卻是樣板（`/{codeTypeNo}`）。把寫死值當一整串文字去驗，**注定驗不過**——程式裡是變數。

拆成：

- **路徑骨幹** 一項：`GET /system/codeType/getOneWithCode`
- **路徑參數的值** 另一項：`TRDETAILKIND`（存成 `param`，不是塞進 api 的 content）

### 代碼表的「資料列」六種類型都裝不下

`TRDETAILKIND` 的五個選項（`1` 自行 / `2` 通匯 / `3` 跨行 / `4` 入帳 / `5` 退款）是資料表 `SYS_CODE_DATA` 的**資料列**——不是欄位（`db_field` 裝不下）、不是程式碼裡的字串（`ui_text` 一定搜不到）。

而這往往正是最該驗的東西（代碼沒建或建錯，畫面下拉就是空的）。做法：

- **不要硬塞進檢查表**（塞進去必然假不符）
- 列進報告的「檢查表範圍外的發現」，寫明「這 N 筆代碼資料需要查資料庫或開畫面確認，靜態驗證涵蓋不到」
- 有 DB 連線的話在第四步順手 `SELECT` 確認

### 同一個東西規格裡有好幾種寫法時，哪個才算

**範例 JSON 最不可信。** 它常是從別支規格複製過來、沒改乾淨的殘留。

真實案例：同一支 API 的查詢參數，規格裡有三種寫法——

| 出處 | 寫的是 | 能不能用 |
|---|---|---|
| 範例 JSON | `startDate` / `endDate` | **不能**，整段是別支規格的殘留 |
| INPUT 欄位表 | `packageTimeS` / `packageTimeE` | **以這個為準** |
| SQL 參考 | `{packupTimeS}` | 不能，那是存儲層的名字不是對外契約 |

抽檢查表時的取用順序：**欄位定義表 > 敘述文字 > 範例**，並與實際的 Controller／VO 程式碼交叉核對。

**API 參數 ≠ 資料表欄位**，兩者同名只是巧合，不同名才是常態。抽的時候分開存成「送出參數」和「資料表欄位」兩類，不要混。

**⚠ 但「引用 vs 定義」不是矛盾。** 母規格填實際值（`TRDETAILKIND`）、共用規格定義樣板（`{codeTypeNo}`），那是正常的引用關係。

只有**同層級的兩份定義互斥**才算矛盾：

| 情況 | 算矛盾嗎 |
|---|---|
| 母規格填值 `TRDETAILKIND`、共用規格定義 `{codeTypeNo}` | **不算**，上層填值下層定義 |
| 同一節的 INPUT 表寫 `packageTimeS`、格式範例寫 `startDate` | **算**，同層級互斥 |
| SA 標必填、SD 標選填 | **算** |

判斷錯了的代價是實的：每份用了共用功能的規格都會生一堆假矛盾，使用者收到 30 條要裁決、其中 25 條是「這是正常引用」——**假矛盾多了之後真矛盾就沒人看了**。

同層級互斥才**記進「規格矛盾／未定義」交使用者裁決，不要自己挑一個**。

## 第二步：程式預檢（advisory，不算數）

```bash
node scripts/spec-check.mjs precheck checklist.json --fe <前端路徑> --be <後端路徑> -o precheck.json
```

純字串比對、零 LLM，用途只有一個：**快速抓錯字**（規格寫「儲存」程式寫「存儲」這類）。

比對規則（`logic` 一律標 manual，程式看不懂行為）：
- `ui_text` → exact substring，全形半形有別、標點有別
- 識別字類 → word-boundary（`pageSize` 不可被 `pageSizeX` 充數）
- `api` → path 正規化（`{id}` = `:id` = `${id}`）+ method 鄰近檢查，允許 Spring 類別層 `@RequestMapping` + 方法層 `@PostMapping` 拆分，但 prefix 與 suffix 必須同一檔案

**預檢結果不算數，不可拿去寫報告的結論。** 它連「該掃哪裡」都會出錯（把 side 標錯，整批 frontend 項目會全部假 missing）。它只是給 implementer 修錯字用的。

## 第三步：獨立 AI 逐項驗證（這個才算數）

派一個**全新 context、沒參與過實作**的 agent，用最強模型（logic 判定沒有任何程式兜底，是最後一道防線，不可降級）。

強制紀律：

1. **讀規格原文**，不是任何人的轉述
2. **收齊整張檢查表**，漏項就是漏驗
3. **逐項開檔驗證**：
   - `ui_text` → 找到**渲染處**（只出現在註解／測試不算）
   - `api` → 真的有 handler／真的有呼叫，不是只出現字串
   - `param` / `response_field` → 欄位確實進出該 API 的 request/response
   - `db_field` → Entity / DDL 確實存在
   - `logic` → **追實際程式流程**（Controller → Service → SQL；元件 → handler → API），親眼看到條件分支／轉換／排序才可判符合。**不可憑檔名、函式名、註解猜**
4. **判 matched 必附證據**：`file:line` + 一句說明

   有功能測試的實測產出時，**優先採用**——它比在原始碼裡搜到強：

   | 檢查項 | 靜態證據 | 實測證據（更強） |
   |---|---|---|
   | 畫面上的文字 | 找到渲染處 | 瀏覽器擷取到的 DOM 文字 |
   | 後端回傳的欄位 | DTO 程式碼 | API 實際回應的欄位 |
   | 行為規則 | 追 Controller → Service → SQL | 實際操作走過的結果 |

   **這一欄是選配，不是階梯。** 沒有實測產出就照靜態證據判，並在報告的證據強度那節寫明「本項未經實測，僅有靜態證據」。**不要為了填這一欄先跑一輪功能測試**。

   但有一種情況靜態真的驗不到：**執行期才決定的內容**（從資料庫代碼檔動態載入的下拉選項、代碼名稱）原始碼裡一定搜不到，光靠靜態驗證會全部判成不符。這種項目老實判不符並寫明原因「執行期載入，靜態驗證涵蓋不到」，或等有實測產出再補。

   證據欄仍要填 `file:line`（第五步驗的是程式碼位置），實測結果寫在說明裡。
5. **寧嚴勿鬆**：找不到、不確定、規格與程式有出入 → 一律 missing
6. **反向掃描規格（防「表抽得少所以全過」）**：重讀規格原文，找檢查表漏抽的項目，補上並一併驗證。**沒有漏抽也要明講「反向掃描無遺漏」** —— 報告要寫出這句，讀者才知道「N 項」是不是就是全部
7. **反向對齊程式（防「多做了沒人發現」）**：反過來枚舉程式對每支 API 實際帶的參數／回傳欄位／查的資料表欄位，跟規格定義的比一比。**程式有、規格沒定義**的欄位列進報告交使用者裁決——是過度實作該移除，還是規格待補。紀律：
   - **只做欄位維度**（參數 / 回傳欄位 / 資料表欄位），**絕不對畫面文字和行為規則反向**（誤報海嘯）
   - 排除基礎設施雜訊：分頁（page/size/offset/limit）、排序（sort/order）、認證 token、時間戳、專案系統共用欄位
   - 規格對某支 API 的欄位定義不完整就略過那支，並註明「規格欄位定義不足，略過」——硬 diff 只會生一堆誤報
   - **範圍上限：只對本次改動涉及的 API 做反向對齊。** 大規格全做，工作量會比正向逐項驗證還大（一支 API 幾十個投影欄位 × 幾支），實務上一定被跳過。與其定一條沒人守的規則，不如明講範圍
8. **規格矛盾**單獨列出交使用者裁決，不可自行取捨
9. **只讀不改**，驗證員不准動任何一行程式碼

**逐項判定之外，把這三件事一併記下來**，它們往往比表內項目更值得看：

| 記什麼 | 為什麼 |
|---|---|
| **檢查表範圍外的問題** | 跨切面的錯誤處理、整支模組沒有單元測試、共用元件的坑——這些不會是任何一條檢查項，但常常比表內的更嚴重 |
| **缺陷的影響範圍** | 缺陷若在共用元件／共用 hook／共用 API，要指出**還有誰會中招**。只說「這一支要修」會讓人以為改一個地方就完事 |
| **證據強度不一樣的地方** | 有 Entity 佐證 vs 只有原生 SQL 字串佐證，可信度差很多。全部混在「符合」裡會讓數字失真 |

輸出 JSON（`review.json`，格式見 `checklist.schema.md`）。

## 第四步：實體 DB 核對（資料表欄位專用）

**規格和程式碼可以一起錯。** 前三步看的都是程式碼——Entity 的 `@Column`、DDL 檔、原生 SQL 字串。
程式碼裡有這個欄位名，只證明有人寫過這個字，證明不了正式資料庫真的有這個欄位。

### 4a. DDL 檔 ↔ Entity（**不需要 DB 連線，一定要做**）

先把程式碼裡的兩份欄位定義互相對過：

- **DDL 檔的 `CREATE TABLE` 欄位名 ↔ ORM／Entity 的 `@Column`** 逐欄一致，含系統共用欄位（建立／修改時間等）
- 兩邊不一致的解讀：
  - **DDL 有、Entity 沒有** → 程式沒用到這個欄位（可能漏做）
  - **Entity 有、DDL 沒有** → DDL 檔沒更新，或 Entity 對錯表

這半段**沒有資料庫也做得到**。下面的 4b 沒連線可以跳過，這一段不行。
兩邊的落差寫進報告「資料表欄位」那一節，跟實體 DB 的結果並列。

### 4b. 對實體資料庫（需要連線）

這一步抓的是程式碼層面看不出來的三種錯：

| 情況 | 為什麼前三步抓不到 |
|---|---|
| DDL 檔寫了但沒套用到正式環境 | 檔案裡有，資料庫裡沒有 |
| Entity 對到另一張同名欄位的表 | `@Column(name="PAY_DATE")` 是對的，`@Table` 指錯表 |
| 規格寫了一個從沒建過的欄位 | 規格與程式都照著抄，兩邊一起錯 |

還有一種最需要這步的情形：**規格提到、但專案裡既沒有 Entity 也沒有 DDL 的表**（欄位只出現在原生 SQL 字串裡）。這種靠程式碼完全無從核對。

### 怎麼取得實體 schema

```sql
SELECT TABLE_NAME, COLUMN_NAME, DATA_TYPE, CHARACTER_MAXIMUM_LENGTH,
       NUMERIC_PRECISION, NUMERIC_SCALE, IS_NULLABLE
  FROM INFORMATION_SCHEMA.COLUMNS
 WHERE TABLE_NAME IN ('表1','表2')
```

只讀 `INFORMATION_SCHEMA`，**不碰任何業務資料表**。連線帳號請用唯讀（`db_datareader`）。
沒有連線權限時，請 DBA 匯出一份 schema 快照：

```bash
sqlcmd -S <server> -d <db> -U <ro_user> -P <pwd> -f 65001 -s "," -W \
  -Q "SET NOCOUNT ON; SELECT TABLE_NAME,COLUMN_NAME,DATA_TYPE,CHARACTER_MAXIMUM_LENGTH,NUMERIC_PRECISION,NUMERIC_SCALE,IS_NULLABLE FROM INFORMATION_SCHEMA.COLUMNS" \
  -o schema.csv
```

然後：

```bash
node scripts/spec-check.mjs dbcheck checklist.json schema.csv
```

### 判定規則

- **實體 DB 明確說沒有這個欄位（或整張表不存在）→ 該項判不符。** 資料庫的答案優先於程式碼——Entity 有 `@Column` 但 DB 沒有，代表 DDL 沒套用或對錯表，那就是真缺陷
- **實體 DB 確實有 → 才可判符合**，證據照舊附程式碼 `file:line`（第五步驗的是程式碼位置，不是 DB）
- **「無從判定」絕不可當成通過。** 那代表沒撈到該表的 schema，不是通過。撈不到就在說明欄據實寫「未經實體 DB 核對」，判定回退到 Entity/DDL 證據
- **型別／長度／可否為空與規格不符**：欄位確實存在 → 不影響符合/不符，改列進報告的「規格矛盾／未定義」交使用者裁決

**沒有 DB 連線也沒有 schema 快照時，整步跳過並在報告寫明「本次未做實體 DB 核對」。** 不可用一句「已確認」帶過——那是自我認證。

## 第五步：證據程式重驗（防唬爛）

```bash
node scripts/spec-check.mjs verify checklist.json review.json --fe <前端路徑> --be <後端路徑>
```

每一筆 matched 證據都真的開檔驗：檔案存在？行號有效？不是產物目錄（node_modules / dist / target / build）？該行 **±10 行**內確實含那串文字？

**引用不實要分兩種，罰則不一樣：**

| 情況 | 處理 |
|---|---|
| 檔案不存在、指到產物目錄、整份 workspace 都找不到那串字 | **造假，整批退回重審**。一筆憑空編造代表整份判定的可信度已經沒了 |
| 行號抓偏（±10 行外但同一個檔案找得到） | **標記修正，不退整批**。改行號重驗那一筆即可 |

分級的理由：把「憑空編造」和「行號差 11 行」罰成一樣，結果是誠實但手抖的判定被判死，而拿 IDE 快取當證據的判定反而全過。

配套：**分歧偵測** —— 程式預檢與 AI 判定相反的項目自動標出，那是人工抽查的靶點（腳本 `verify` 會印）。

## 第六步：寫報告

見 `report-template.md`。報告是給**人**看的（客戶、科長、PM），不是給工具看的。

## 報告白話鐵律

報告裡出現任何需要讀者「去查別的東西才看得懂」的字，就是失敗。

**不准出現在報告裡：**
- 內部識別碼：`runId`、`taskId`、`78f07ea1-...`、`noteId`
- 工具內部術語：`matched` / `missing` / `manual` / `advisory` / `itemType` / `carryForward` / `閘門`
- **`waive` / `waived` 這個字**（資料裡的 `status: waived` 照用，但報告要寫「已豁免」並**緊接寫出豁免的實際原因**——只寫「已豁免」讀者不知道那是什麼）
- 型別代號當標題：`logic`、`ui_text`、`db_field`
- **編號式交叉引用**：「見缺陷 2」「同第 5 項」—— 讀者得回頭數才知道在講什麼。**交叉引用要叫出名字**：「見『後端排序完全沒接上』」。優先順序表、規格矛盾清單這種會回指缺陷的地方最容易犯

**換成：**

| 內部說法 | 報告寫法 |
|---|---|
| matched / missing | 符合 / 不符 |
| manual | 需人工判斷 |
| itemType: logic | 行為規則（畫面怎麼動、後端怎麼算） |
| itemType: ui_text | 畫面上的文字 |
| itemType: api | API 路徑與 HTTP 方法 |
| itemType: param | 送給後端的參數 |
| itemType: response_field | 後端回傳的欄位 |
| 證據 `file:line` | 程式碼位置 |
| advisory，不解鎖閘門 | 不算數 —— 只能比對文字，看不懂行為 |
| matched_path_only | （直接寫實際原因，見下） |

**最重要的一條：分類標籤不能取代原因。**

不要寫「這 8 項屬於證據形式問題，建議豁免」—— 讀者不知道那是什麼。直接寫發生什麼事：

> 前端是用 `` `${API_RELATED_LIST}/${type}/...` `` 組出路徑的，路徑常數和 method 不在同一行，所以逐行比對抓不到。程式本身沒問題。

「什麼原因」要寫到讀者當場就懂，不用回頭查任何東西。

## 報告必備段落

1. **結果總表** —— 各種驗法的數字並列，並明講哪個算數哪個不算；有做實體 DB 核對就獨立一列，沒做要寫「本次未做」。**反向掃描補了幾項要在這裡交代**（沒補也要寫「無遺漏」），否則讀者無從判斷這 N 項是不是全部
2. **不符的分兩類**：A. 程式真的做錯或沒做（要修）／B. 程式是對的，是驗證方式抓不到（不用修）。**混在一起講會讓讀者以為系統爛掉了**
3. **每個真缺陷**：規格怎麼寫 → 程式實際狀況（附行號）→ 使用者會遇到什麼 → 怎麼修。缺陷若由多條檢查項組成，標明涵蓋哪幾項；缺陷若在共用元件，標明還有誰會中招
4. **B 類每一項要寫出實際原因，並回頭檢討檢查表** —— 抓不到常常不是驗證方式的錯，是**檢查項當初抽錯粒度**（例：把常數值寫進 API 路徑、把帶參數的完整路徑當一整串文字驗，注定驗不過）。寫下「下次應該怎麼抽」，否則下一份報告照錯一次
5. **程式檢查與 AI 判斷結論相反的** —— 腳本的分歧偵測會列出來。兩邊用不同方法看同一件事卻得到相反結論，代表至少有一邊在這裡不管用，最值得人花一分鐘看一眼
6. **規格矛盾／未定義** —— **全列，不挑重點**。挑掉的那條往往就是下一個人踩到的。量大就分「讀規格階段發現」與「對照程式碼才浮現」兩組，但不可只留摘要
   - **同一個根因可以併成一條，但受影響的欄位要列齊**（例：「OUTPUT 表少了 16 個 SQL 投影欄位」列出全部 16 個名字）。16 條同根因的項目會把另外 6 個真正獨立的問題灌到看不見
7. **反向對齊結果** —— 程式有、規格沒定義的欄位；沒有也要寫「無多餘欄位」
8. **資料表欄位：DDL↔Entity 的落差 + 對實體 DB 的結果** —— 幾個確實有、幾個沒有、幾個無從判定。**無從判定要列出是哪些表、為什麼撈不到**；沒做實體核對要寫明「本次未做」並說清楚現有證據強度到哪
9. **檢查表範圍外的發現** —— 跨切面問題、測試覆蓋缺口、共用元件的坑、代碼表資料列這種檢查表裝不下的東西
10. **建議優先處理** —— **先寫出排序準則**（例：依「上線後被發現的機率 × 後果」），再列清單。沒寫準則的排序，讀者不知道憑什麼這樣排，也就無法反對
11. **逐條結果明細** —— 全部項目列表，不符的排在每類最前面

明細表格最多五欄（編號 / 狀態 / 檢查項 / 程式碼位置 / 規格出處）。**欄位一多，證據欄會被擠成一個字一行**，整張表就廢了。判定理由放前面的分節展開，不要塞進表格。

行為規則那一類的「程式碼位置」是**該行為實作所在的位置**，不是規格文字出現的位置——報告要註明這件事，否則讀者會拿去逐字比對然後以為證據錯了。

## 跟另兩份的分工

| 這份不管，交給誰 | 為什麼 |
|---|---|
| 服務起不來、API 回 500、資料沒真的落地、畫面跑版 | 功能測試（`verifying-end-to-end`）。這份只讀不跑，證明不了跑起來會不會壞 |
| 規格自己前後矛盾（SA↔SD、同一份文件內部打架） | `spec-consistency-check`。這份撞到就記進「規格矛盾／未定義」，但系統性地找應該開工前用那份做完 |

**建議順序**：這份的**第一步（抽檢查表）先做**，那張表同時是本份的驗證基準、也是功能測試的案例來源。接著跑功能測試，最後回來做第二～六步的判定，就能採用它留下的實測證據。

判定放最後的理由：那些執行期才決定的內容（動態載入的選項文字之類），靜態驗證一定判成查不到，實測開畫面看一眼就有答案。

## 絕對禁止

- implementer 自評（驗證員必須是沒看過實作過程的獨立 agent）
- 只看 commit message、回報摘要下判定 —— 必須自己開檔核對
- matched 不附證據、證據指不到原始碼位置
- 把規格矛盾自行取捨掉
- 驗證員修改任何程式碼
- 用預檢分數寫報告結論
- 把「沒撈到 schema」當成「實體 DB 核對通過」
- 沒做實體 DB 核對卻在報告寫「已與資料庫確認」
- **規格矛盾只挑重點列**（挑掉的那條就是下一個人踩到的）
- 做了反向掃描卻不在報告交代結果（讀者無從判斷項數是不是全部）
- 只報表內項目，把撞見的跨切面問題吞掉
