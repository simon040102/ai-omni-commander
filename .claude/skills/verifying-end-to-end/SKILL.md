# 功能測試（完整功能的 CRUD／端到端，不是單一 function）

驗證**整條功能通路的真實性**：服務真的起來、API 真的回應、資料真的進 DB、畫面真的操作得下去。

**這份只驗現實，不驗規格。** 「程式有沒有照規格做」是另一件事（見下方「跟另兩份的分工」）——這裡問的是：不管規格寫什麼，這條路走不走得通。

與單元測試的分工：**單元測試只驗邏輯，不驗 SQL 和欄位名——mock 掉資料層的測試測不出欄位打錯。功能測試是真服務、真 DB、真瀏覽器，那才是真正的驗收。**

## 開始前要有

### 驗收清單（報告有哪幾項）

**沒有現成的就自己列，但要在報告標明「本次驗收項目為自列」。** 沒有標明的話，讀報告的人會以為這份清單是別人核准過的範圍。

最小清單就是下面這幾項，照你手上有的環境刪減：

| 項目 | 沒有這個環境時 |
|---|---|
| 單元測試全數通過 | 專案沒設測試指令 → 標 N/A + 原因 |
| API 煙霧測試 | 後端起不來 → FAIL（不是 N/A） |
| 資料異動驗證 | 沒有寫入操作 → 標 N/A + 原因 |
| 前端編譯零錯誤 | 純後端任務 → 標 N/A |
| 瀏覽器實測 | 純後端任務 → 標 N/A |
| 靜態關卡 | 沒有變更範圍可掃 → 標 N/A + 原因 |

**單元測試算在這份裡。** 開頭講的「分工」是說它證明不了功能可用，不是說不用跑——有測試指令就跑，把結果填進總表第一列。

### 檢查表（每一項實際要測什麼）

要測什麼的清單：API、送出參數、回傳欄位、資料表欄位、畫面文字、行為規則。三種情況：

| 手上有什麼 | 怎麼辦 | 這次的 PASS 代表什麼 |
|---|---|---|
| 有檢查表 | 直接用 | 程式**合規**且跑得起來 |
| 只有規格 | 先拆成逐條檢查項（`spec-compliance-review` 第一步，格式見下） | 同上 |
| 只有口述的 bug／需求 | 抽 **bug 原文**的重現步驟與預期行為 | 這個 bug 修好了 |
| **什麼都沒有**（要驗一個現成在跑的東西） | **從程式碼契約推導**：route 定義、Controller、DTO、Entity | **只證明程式自洽，不證明合規** |

最後一種最常見（回歸驗證、接手驗收、「你去測一下能不能用」），而且**必須在報告每一項標註「參數來源＝程式碼，非規格」**。不標的話，這種 PASS 會被當成合規證明，那是假的——程式碼是被驗的對象，拿它當預期值是循環論證。

檢查表的最小格式（自己列的時候照這個）：

| 這是什麼 | 內容 | 從哪推來的 |
|---|---|---|
| API | `POST /api/order/search` | route 定義 / 規格 |
| 送出參數 | `payDateS`、`kindNo` | Controller 簽章 / 規格 INPUT 表 |
| 回傳欄位 | `resultList[].orderNo` | DTO / 規格 OUTPUT 表 |
| 畫面文字 | 按鈕「查詢」、錯誤訊息全文 | 規格（**程式碼推不出來，只能標 N/A**） |
| 行為規則 | 「未勾選就送出要擋下」 | 規格 / bug 原文 |

**畫面文字這類不可能從程式碼推導**（推出來的就是程式碼自己），沒有規格時整類標 N/A，不要假裝驗過。

### 環境

- **服務啟動方式**：workspace 的啟動指令／dev server
- **DB 連線**：驗證資料落地用，可讀查詢
  - 這裡用 schema 是為了**取得欄位名去組 SQL 查資料**。「欄位名對不對規格」不在這裡判定（那是 `spec-compliance-review` 的事）

## 整體流程

1. **備齊驗收清單 + 檢查表**（都沒有就照上面自己列，並標明是自列）
   - 兩者不適用的項目一律回報 **N/A + 原因**，不要留空也不要推 PASS
   - **憑印象測等於自己又拆了一次規格，還拆得比較差**
2. **服務先起來**：後端起服務、前端起 dev server——**服務起不來本身就是第一個 FAIL**
3. **逐項實測**：後端 API 真請求 + 資料落地／前端瀏覽器操作（見下）
4. **逐項回報結果**：每項 PASS/FAIL 如實記錄，截圖與擷取到的文字存成檔案（路徑見「證據要留下來」）
5. **FAIL 就是不能交付**：任何一項最新結果為 FAIL，這支功能不算完成；修復後**重測**該項並回報 PASS 才放行（不是改回報，是重測）

## 後端功能測試

### 1. API 煙霧測試（每一個新增／修改的 API 都要測）

- 服務啟動後，用 curl／HTTP client **實測每支 API**：確認回 200，不是 500
- 帶著**實形狀的真參數**（照檢查表的「送出參數」項），不是空 body 混過去
- **驗回應結構**：欄位名與檢查表的「回傳欄位」逐欄對得起來（這裡才抓得到 DTO 欄位打錯字）
- **錯誤路徑也要測**：必輸欄位缺漏、查無資料的 id——確認回的是檢查表定義的錯誤格式，不是 stack trace

**⚠ 參數名只從檢查表拿，不要自己另找來源。** 打不動的時候很容易去翻規格的範例 JSON、或直接拿 DB 欄位名來湊——兩個都會錯：

- **規格的範例 JSON 常是別支規格的殘留**，參數名跟實際契約不一樣（怎麼判斷哪個才對，是 `spec-compliance-review` 第一步的事，不是這裡）
- **API 參數 ≠ DB 欄位**。`packageTimeS`（對外契約）和 `PackupTime`（存儲欄位）是兩回事。DB schema 是用來驗**回傳資料對不對**的，不是用來組請求的

**檢查表對不上實際程式時的兩條路**（不要自己猜一個能打通的參數名就當測過）：

- **有檢查表、但對不上** → 回報「無法測試 + 原因」，並把落差交出去。這是規格與程式的落差，該被看見
- **沒有檢查表** → 從程式碼契約（Controller 簽章、DTO、route 定義）推導參數，**但每一項要標註「參數來源＝程式碼，非規格」**

兩條路都不可以做的是：猜一個能打通的參數名、測出 200、報 PASS 卻不留痕跡。那樣會有一支從沒被真正測到的 API 上線。

### 2. 資料異動驗證（CRUD 真的落地）

每個寫入操作做完，**直接查 DB 驗證**：

- **新增** → count/sample 查得到該筆，欄位值正確
- **修改** → sample 確認欄位值已更新
- **刪除** → count 查不到（或依檢查表定義為軟刪除標記）
- 欄位名以 **DB schema 實際定義為準，嚴禁猜**
- 系統共用欄位（建立／修改時間等）也要確認有寫入

### 3. 靜態關卡檢查

- **seed SQL**：INSERT 欄位數量與 VALUES 參數數量一致
- **效能紅線**：資料存取層沒有「撈全表 + 記憶體過濾」的查詢

這兩條掃的是**本次變更範圍**（diff／任務涉及的檔案）。沒有變更範圍可掃時（驗一個現成的東西）→ 標 **N/A + 寫明「無變更範圍」**，不要靜默跳過。

> 資料表欄位對不對**不在這裡驗**。程式碼裡的欄位定義（DDL 檔、Entity）比對，以及「正式資料庫到底有沒有這個欄位」，都由 `spec-compliance-review` 負責（它會直接查 `INFORMATION_SCHEMA`，比程式碼互比徹底）。這裡只管**資料有沒有真的進去**。

## 前端功能測試

### 1. 編譯零錯誤

`tsc --noEmit` 零錯誤（build 過不代表型別乾淨）

### 2. 瀏覽器實測（Playwright，照使用者的操作流程走）

照檢查表的「行為規則」項**完整走一遍功能**，不是只開頁面看有沒有渲染：

- **查詢**：輸入條件 → 送出 → 結果正確過濾、分頁／排序可用
- **新增**：開表單 → 填檢查表的送出參數 → 送出 → 成功訊息與清單更新
- **修改**：選一筆 → 改欄位 → 儲存 → 值有更新
- **刪除**：刪除 → 確認彈窗（檢查表有這條的話）→ 清單消失
- **失敗路徑**：必填空值送出 → 出現檢查表的錯誤訊息文字（逐字）
- 有跳窗／連動欄位的，把連動行為走過（如選某項 → 欄位必填變更）

**擷取到的 DOM 文字要留下來，存成檔案。** 那是「畫面真的顯示出這幾個字」的直接證據，比在原始碼裡搜到強得多——執行期才從資料庫載入的下拉選項、代碼名稱，靜態搜尋一定找不到，只有這裡看得到。

存法（不要留在工具的暫存目錄，那裡檔名是時間戳，別人不會知道去哪找）：

```
docs/verification-reports/{功能代碼}-dom.md
```

內容一行一筆，另外把執行期載入的內容單獨列一節：

```markdown
## 畫面文字
查詢按鈕 → 查詢
清算金額起 → 清算金額(起)
必填錯誤訊息 → 請選擇付款日期（起）

## 執行期載入的（靜態搜尋找不到，這節最重要）
查詢類別下拉 → 全部 / 跨存FEDI / 自行 / 通匯 / 入帳 / 退款
```

截圖跟它放同一個目錄。`spec-compliance-review` 判定時會直接採用這份。

### 3. 證據：斷言 + 截圖，兩者分工不同

| | 抓得到 | 抓不到 |
|---|---|---|
| **DOM 文字／狀態擷取** | 筆數錯、資料錯、條件沒帶到、錯誤訊息文字 | 版面爛掉 |
| **看截圖** | 元素被遮住、跑版、彈窗沒渲染、CSS 掉了 | —— |

只有截圖沒斷言 → 你在用眼睛做本來該機器做的事。
只有斷言沒截圖 → 「文字都對但畫面根本不能用」會漏掉。

**做法：**
- 斷言優先用擷取的文字／狀態（筆數、關鍵欄位值、錯誤訊息逐字）
- 截圖必須 **fullPage**（含捲軸內容）
- **被引用為 PASS 依據的關鍵畫面，必須實際讀過截圖，並在報告寫出看到什麼**——「清單 14 筆、第一列封包數 3、檢視跳窗開啟且封包內容有 3 段」。**寫不出具體內容就是沒看。**
- 不必每張都讀（讀圖很吃 context），但凡是拿來當通過依據的，一定要讀

**⚠ 引用截圖前先確認圖寬 ≥ viewport 寬。** 截圖工具有時會少截右側，畫面上看起來像跑版、按鈕不見、文字被切一半，其實是圖的問題不是頁面的問題。

真實案例：截出來 1269×603、viewport 是 1396×663，右側 9% 被切掉，狀態欄的 `completed` 只剩「complet」。查 `scrollWidth === clientWidth` 才確認頁面沒事。**照著這個誤報下去，就會去修一個不存在的 bug。**

**「有截圖」不等於「有通過」。** 另一個真實案例：截了圖、隔很久才去看，一看才發現 CORS 把整頁擋掉、表格 0 列——檔案一直都在，只是沒人看。

## 報告格式

**總表放最上面，細節放下面。** 人看報告先要的是「幾項過、哪幾項沒過」，不是一路讀到底：

```markdown
## 驗收結果

| 項目 | 結果 | 依據 |
|---|---|---|
| 單元測試 | PASS | 17/17 通過 |
| API 煙霧測試 | PASS | GET /order/1001 → 200，5 欄與檢查表的回傳欄位逐欄相符 |
| 資料異動驗證 | **FAIL** | 詳見下方「未通過項目」 |
| 瀏覽器測試 | PASS | 清單 14 筆、明細跳窗正常，截圖 xxx.png |

## 未通過項目
### 資料異動驗證
（觸發條件、實際錯誤訊息、影響範圍、重現步驟）
```

## 不要自己標嚴重程度

嚴重程度是**業務判斷**——這支功能一天幾個人用、出錯是擋交易還是顯示難看、下週上版還是下季，這些你都不知道。

**陳述觸發條件與影響範圍，讓人自己判斷：**

- ❌「嚴重問題：檢視功能無法使用」
- ✅「`get()` 在明細筆數 > 1 時必定回 500；單筆不受影響」

## 逐項回報與閘門

- 每個驗收項如實回報 PASS/FAIL + 說明；FAIL 不可隱瞞、不可「大致可以」混過
- **驗收 FAIL 擋結案**：任何驗收項最新一筆結果為 FAIL，結案被阻擋；修復後**重測**該項並回報 PASS 才放行（不是改回報，是重測）
- 環境因素測不了（服務起不來、DB 連不上）→ 如實回報「無法測試 + 原因」，交使用者處理，**不可推 PASS 也不可偽裝測過**

## 跟另兩份的分工

| 這份不管，交給誰 | 為什麼 |
|---|---|
| 程式有沒有照規格做（欄位名、畫面文字、行為規則逐條對） | `spec-compliance-review`。它讀規格原文逐條開檔核對，判定要由**沒參與過實作的人**做——這份通常是實作者自己跑，不符合那個條件 |
| 資料表欄位對不對（含正式資料庫到底有沒有這個欄位） | 同上，它會直接查 `INFORMATION_SCHEMA` |
| 規格自己前後矛盾（SA↔SD、同一份文件內部打架） | `spec-consistency-check`。只需要規格文件，跟程式無關，開工前就該做完 |

**建議順序**：先產出檢查表 → 跑這份（拿檢查表當案例，順手留下 DOM 文字、API 實際回應、DB 查詢結果）→ 再跑 `spec-compliance-review` 判定，它可以直接採用這份留下的證據。

反過來（先判定再測）也能跑，只是那些執行期才決定的內容（動態載入的選項文字之類）會判成「查不到」。

## 絕對禁止

- 只跑單元測試就宣稱功能可用（UT 綠 ≠ API 通）
- API 只驗 200 不驗回傳欄位形狀
- 寫入操作不查 DB 就當作落地
- 用「程式碼看起來對」代替實際操作
- FAIL 改成 PASS 而沒有重測
- 未回報測不出錯的部分
- 沒有檢查表卻不標註「參數來源＝程式碼」，讓程式自洽的 PASS 看起來像合規
- 拿規格的範例 JSON 或 DB 欄位名湊參數（前者常是別支規格的殘留，後者不是對外契約）
- 自列驗收清單卻不標明是自列
- 自己給問題標「嚴重」「高風險」等級
- 附了截圖卻沒讀過內容就當通過
