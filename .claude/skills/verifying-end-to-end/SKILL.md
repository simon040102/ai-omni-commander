# 功能測試（完整功能的 CRUD／端到端，不是單一 function）

驗證**整條功能通路的真實性**：服務真的起來、API 真的回應、資料真的進 DB、畫面真的操作得下去。

與單元測試的分工：**單元測試只驗邏輯，不驗 SQL 和欄位名——mock 掉資料層的測試測不出欄位打錯。功能測試是真服務、真 DB、真瀏覽器，那才是真正的驗收。**

## 開始前要有

- **驗收清單**：依任務類型（前端／後端）取得的逐項驗收項目
- **功能規格**：SA/SD 文件路徑——操作流程與預期行為的依據
- **服務啟動方式**：workspace 的啟動指令／dev server
- **DB 連線**：驗證資料落地用，可讀查詢

## 整體流程

1. **取驗收清單**：依任務 label（前端／後端）取得逐項驗收項目
   - 專案有設定測試指令時，清單會自動前置「單元測試全數通過」項
   - label 非前端／後端／fullstack 時回傳完整清單，不適用的項目回報 `passed=true` + `note="N/A"`
2. **服務先起來**：後端起服務、前端起 dev server——**服務起不來本身就是第一個 FAIL**
3. **逐項實測**：後端 API 真請求 + 資料落地／前端瀏覽器操作（見下）
4. **逐項回報結果**：每項 PASS/FAIL 如實記錄，截圖等證據上傳檔案
5. **閘門**：任何驗收項最新一筆結果為 FAIL → 結案被阻擋，修復後重測回報 PASS 才放行

## 後端功能測試

### 1. API 煙霧測試（每一個新增／修改的 API 都要測）

- 服務啟動後，用 curl／HTTP client **實測每支 API**：確認回 200，不是 500
- 帶著**實形狀的真參數**（照 SD 的 INPUT 定義），不是空 body 混過去
- **驗回應結構**：欄位名與 SD 的 OUTPUT 定義一致（這裡才抓得到 DTO 欄位打錯字）
- **錯誤路徑也要測**：必輸欄位缺漏、查無資料的 id——確認回的是規格定義的錯誤格式，不是 stack trace

**⚠ SD 的範例 JSON 不可照抄。** 範例常是從別支規格複製過來沒改乾淨的殘留。參數名以 **INPUT 欄位表**為準，並與實際的 Controller／VO 程式碼交叉核對。

真實案例：同一支 API 的查詢參數在規格裡有三種寫法——範例 JSON 寫 `startDate`／`endDate`（整段是別支規格的殘留）、INPUT 表寫 `packageTimeS`／`packageTimeE`、SQL 寫 `{packupTimeS}`。照範例抄一定測不動。

**規格自相矛盾時：開規格缺口交人裁決，不要自己猜、也不要照抄。** 規格寫錯不是「測不出來」的藉口——照抄爛範例、測出 200、報 PASS，結果是沒測到的 API 上線了。

**注意：API 參數 ≠ DB 欄位。** `packageTimeS`（對外契約）和 `PackupTime`（存儲欄位）是兩回事，拿 DB 欄位去組 request 一定失敗。DB schema 是用來驗**回傳資料對不對**的，不是用來組請求的。

### 2. 資料異動驗證（CRUD 真的落地）

每個寫入操作做完，**直接查 DB 驗證**：

- **新增** → count/sample 查得到該筆，欄位值正確
- **修改** → sample 確認欄位值已更新
- **刪除** → count 查不到（或依規格為軟刪除標記）
- 欄位名以 **DB schema 實際定義為準，嚴禁猜**
- 系統共用欄位（建立／修改時間等）也要確認有寫入

### 3. 靜態關卡檢查

- **DDL 比對**：CREATE TABLE 欄位名與 ORM/Entity 定義逐欄一致（含系統共用欄位）
- **seed SQL**：INSERT 欄位數量與 VALUES 參數數量一致
- **效能紅線**：資料存取層沒有「撈全表 + 記憶體過濾」的查詢

## 前端功能測試

### 1. 編譯零錯誤

`tsc --noEmit` 零錯誤（build 過不代表型別乾淨）

### 2. 瀏覽器實測（Playwright，照使用者的操作流程走）

照 SA 的操作情境**完整走一遍功能**，不是只開頁面看有沒有渲染：

- **查詢**：輸入條件 → 送出 → 結果正確過濾、分頁／排序可用
- **新增**：開表單 → 填規格定義的欄位 → 送出 → 成功訊息與清單更新
- **修改**：選一筆 → 改欄位 → 儲存 → 值有更新
- **刪除**：刪除 → 確認彈窗（若規格有定義）→ 清單消失
- **失敗路徑**：必填空值送出 → 出現規格定義的錯誤訊息（逐字）
- 有跳窗／連動欄位的，把連動行為走過（如選某項 → 欄位必填變更）

### 3. 證據：斷言 + 截圖，兩者分工不同

| | 抓得到 | 抓不到 |
|---|---|---|
| **DOM 文字／狀態擷取** | 筆數錯、資料錯、條件沒帶到、錯誤訊息文字 | 版面爛掉 |
| **看截圖** | 元素被遮住、跑版、彈窗沒渲染、CSS 掉了 | —— |

只有截圖沒斷言 → 你在用眼睛做本來該機器做的事。
只有斷言沒截圖 → 「文字都對但畫面根本不能用」會漏掉。

**做法：**
- 斷言優先用擷取的文字／狀態（筆數、關鍵欄位值、錯誤訊息逐字）
- 截圖必須 **fullPage**（含捲軸內容）
- **被引用為 PASS 依據的關鍵畫面，必須實際讀過截圖，並在報告寫出看到什麼**——「清單 14 筆、第一列封包數 3、檢視跳窗開啟且封包內容有 3 段」。**寫不出具體內容就是沒看。**
- 不必每張都讀（讀圖很吃 context），但凡是拿來當通過依據的，一定要讀

**「有截圖」不等於「有通過」。** 真實案例：截了圖、隔很久才去看，一看才發現 CORS 把整頁擋掉、表格 0 列——檔案一直都在，只是沒人看。

## 報告格式

**總表放最上面，細節放下面。** 人看報告先要的是「幾項過、哪幾項沒過」，不是一路讀到底：

```markdown
## 驗收結果

| 項目 | 結果 | 依據 |
|---|---|---|
| 單元測試 | PASS | 17/17 通過 |
| API 煙霧測試 | PASS | GET /order/1001 → 200，5 欄與 SD OUTPUT 逐欄相符 |
| 資料異動驗證 | **FAIL** | 詳見下方「未通過項目」 |
| 瀏覽器測試 | PASS | 清單 14 筆、明細跳窗正常，截圖 xxx.png |

## 未通過項目
### 資料異動驗證
（觸發條件、實際錯誤訊息、影響範圍、重現步驟）
```

## 不要自己標嚴重程度

嚴重程度是**業務判斷**——這支功能一天幾個人用、出錯是擋交易還是顯示難看、下週上版還是下季，這些你都不知道。

**陳述觸發條件與影響範圍，讓人自己判斷：**

- ❌「嚴重問題：檢視功能無法使用」
- ✅「`get()` 在明細筆數 > 1 時必定回 500；單筆不受影響」

## 逐項回報與閘門

- 每個驗收項如實回報 PASS/FAIL + 說明；FAIL 不可隱瞞、不可「大致可以」混過
- **驗收 FAIL 擋結案**：任何驗收項最新一筆結果為 FAIL，結案被阻擋；修復後**重測**該項並回報 PASS 才放行（不是改回報，是重測）
- 環境因素測不了（服務起不來、DB 連不上）→ 如實回報「無法測試 + 原因」，交使用者處理，**不可推 PASS 也不可偽裝測過**

## 絕對禁止

- 只跑單元測試就宣稱功能可用（UT 綠 ≠ API 通）
- API 只驗 200 不驗回傳欄位形狀
- 寫入操作不查 DB 就當作落地
- 用「程式碼看起來對」代替實際操作
- FAIL 改成 PASS 而沒有重測
- 未回報測不出錯的部分
- 照抄 SD 的範例 JSON 當測試參數
- 自己給問題標「嚴重」「高風險」等級
- 附了截圖卻沒讀過內容就當通過
